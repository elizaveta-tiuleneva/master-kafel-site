# Настройка Supabase

Сайт использует **два независимых проекта Supabase** с одинаковой структурой:

| | Тестовый | Рабочий |
|---|---|---|
| Аккаунт | разработчика | владельцев компании |
| Данные | демо-проекты, тестовые заявки | только реальные |
| Когда создаётся | сейчас, для разработки | перед запуском сайта |
| Адрес и ключ | `.env.local` у разработчика | переменные окружения на хостинге |

Данные между проектами **не переносятся**. В рабочий проект разворачивается только структура
из `supabase/migrations/`.

Тариф — **Free**. Ничего платного включать не нужно. Ограничения бесплатного тарифа:
500 МБ базы, 1 ГБ файлов, 5 ГБ трафика в месяц, 2 активных проекта на организацию;
**проект ставится на паузу после 7 дней без активности** (на тестовом это нормально —
его можно разбудить кнопкой Restore; для рабочего сделаем еженедельный пинг).
Условия: https://supabase.com/pricing

## Часть 1. Тестовый проект (делает разработчик сейчас)

### Шаг 1. Аккаунт и организация

1. Откройте https://supabase.com/dashboard и войдите (email или GitHub).
2. Если попросит создать организацию: название, например, `master-kafel-dev`,
   тип — Personal, план — **Free**.

### Шаг 2. Новый проект

1. **New project**.
2. Name: `master-kafel-test`.
3. Database Password: нажмите **Generate a password** и сохраните пароль в менеджере паролей.
   В код и в чат его не вставлять. Для работы сайта он не нужен.
4. Region: **Northeast Asia (Seoul)** — ближе всего к посетителям из Кореи.
5. **Create new project**. Подождите 1–2 минуты, пока проект создаётся.

### Шаг 3. Структура базы

1. Слева **SQL Editor** → **New query**.
2. Откройте файл `supabase/migrations/20261102120000_initial_schema.sql`,
   скопируйте всё содержимое, вставьте в редактор.
3. **Run**. Должно появиться «Success. No rows returned».
4. Проверка: слева **Table Editor** — таблицы `admins`, `projects`, `project_photos`,
   `leads`, `lead_files`; у каждой значок RLS включён.
   **Storage** — две корзины: `project-photos` (Public) и `lead-files` (Private).

Если появилась ошибка — не исправляйте SQL сами, пришлите мне текст ошибки.

### Шаг 4. Запретить самостоятельную регистрацию

1. **Authentication** → **Sign In / Providers** (раздел общих настроек Auth).
2. Выключите **Allow new users to sign up** → **Save**.
3. Убедитесь, что провайдер **Email** включён.

Теперь войти могут только пользователи, созданные вручную.

### Шаг 5. Администратор

1. **Authentication** → **Users** → **Add user** → **Create new user**.
2. Email и пароль для входа в админку. Отметьте **Auto Confirm User**.
3. **SQL Editor** → New query → вставьте содержимое `supabase/snippets/add-admin.sql`,
   замените `ADMIN_EMAIL` на этот email **только в редакторе** (файл в проекте не меняйте) → **Run**.
4. Внизу должна появиться одна строка с этим email.

### Шаг 6. Ключи для сайта

1. **Project Settings** → **API Keys**.
2. Скопируйте **Publishable key** (`sb_publishable_...`).
   Адрес проекта (`https://….supabase.co`) — там же или в окне **Connect**.
3. В папке проекта скопируйте `.env.example` в `.env.local` и заполните:
   ```
   VITE_SUPABASE_URL=https://ваш-проект.supabase.co
   VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_...
   ```
4. **Secret key** (`sb_secret_...`) и legacy `service_role` **никуда не копируйте** — ни в
   `.env.local`, ни в чат. Они понадобятся только серверным функциям и будут храниться в
   Supabase → Edge Functions → Secrets.

Publishable key по документации Supabase безопасно размещать в браузере: доступ ограничивают
правила RLS из миграции.

### Шаг 7. Сообщите разработчику

Напишите «тестовый проект готов». Ключи присылать не нужно: `.env.local` лежит у вас в папке
проекта, и сайт прочитает его сам.

## Часть 2. Рабочий проект (перед запуском, аккаунт владельцев)

1. Владельцы регистрируются на https://supabase.com своей рабочей почтой, создают организацию
   (план Free) и приглашают разработчика: **Organization Settings → Team → Invite** с ролью
   **Developer** (не Owner).
2. Новый проект `master-kafel` в регионе **Northeast Asia (Seoul)**. Пароль базы хранят владельцы.
3. Шаги 3–5 из части 1: та же миграция, запрет регистрации, учётная запись администратора
   **на email владельцев**.
4. Серверные функции и их секреты (Telegram, DeepL) разворачиваются заново в этом проекте —
   инструкция появится на этапах 4–5.
5. На хостинге (Cloudflare Pages) в переменных окружения рабочего сайта указываются адрес и
   publishable key **рабочего** проекта. `VITE_SHOW_DEMO_PROJECTS` не задаётся.
6. Владельцы загружают реальные проекты через админку; проверяем все функции.
7. После передачи владельцы удаляют разработчика из организации.

Тестовый проект остаётся у разработчика или удаляется — с рабочим он никак не связан.

## Если в будущем меняется структура базы

Каждое изменение — новый файл в `supabase/migrations/` с датой в имени. Файлы выполняются по
порядку в обоих проектах. Старые файлы миграций не редактируются.
